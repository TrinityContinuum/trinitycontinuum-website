## Cloudflare Access deployment boundary (verified against Cloudflare Workers docs, Nov 23, 2026)
- **Do not put Worker-wide Access on `trinity-independent-booking`** if it also serves public `/api/public/policy`, `/api/public/slots`, or `/api/public/book`. Worker-wide Access would require visitor sign-in and break customer-facing booking. Instead create **path/hostname-scoped Cloudflare Access applications** that actually cover `/admin` and **every** `/api/admin/*` path on each reachable hostname, or split private administration into a separate Access-protected Worker. Evaluate all `workers.dev`, preview, custom-domain and route entry points; never assume a single hostname policy covers them all.
- The staged private gate reads `await ctx.access.getIdentity()` and matches `identity.email` against private `ADMIN_APPROVER_EMAILS` **plus** the existing `ADMIN_PASSWORD`. `ctx.access.email` is not Cloudflare's authenticated API, and client-supplied identity headers are not substitutes.
- Access identity is present only when Access actually authenticates the invocation. Tests with mocked `ctx.access` validate code paths, not live Access/MFA configuration. Identity can be absent for certain internal/static-asset routing, service bindings or WARP contexts; keep access fail-closed and verify the real deployed route.
